## Conformance notes

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/florence2_vision_language_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 12-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision it was generated from, the module SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/florence2_vision_language_input_manifest.json` — a top-level record naming the demonstrated tasks plus one per-capability manifest under `capabilities`, with the schema, ceilings, observed input, generation settings, verdict, and one recorded rejection finding from the unsupported-task probe; `evaluation_report` (EVAL21) writes `outputs/florence2_vision_language_evaluation_report.json` — one combined report over all three capabilities whose `capabilities` sub-reports carry each task's own verdict.
- The notebook exercises `Florence2Pipeline` through the carried module rather than reimplementing model inference; the pipeline pins the immutable community-converted revision (`florence-community/Florence-2-large`, loadable with `trust_remote_code=False`), stages the missing weight file through `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses a checkpoint that does not map cleanly onto the native architecture. The notebook never calls `transformers`, `huggingface_hub` or `.generate(` directly, and its only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- MULTI-CAPABILITY obligations (INF10): three task tokens are demonstrated with their own stated input/output contracts (`<CAPTION>` -> str; `<OD>` -> boxes + labels in input pixels, no scores; `<OCR>` -> str); each capability's request is validated separately through `validate_inputs` and each gets its own evaluation sub-report; generation settings (`max_new_tokens`, `num_beams` = `NUM_BEAMS`, `do_sample=False`) are explicit per call (INF8/INF9); the six other exposed task tokens are listed as exposed-but-not-demonstrated, and segmentation, region-to-category/description, open-vocabulary detection, VQA and batching are stated as not provided (G7/ID6).
- Metrics (EVAL1/EVAL7/EVAL9): only OCR has a helper (`character_error_rate`), applied to the drawn text on the default sample as a sanity check and to `OCR_REFERENCE` on BYOD; captions and detections have no metric, their sub-reports are `not-measurable`, and each says what labelled data it would need. The previous notebook's notebook-local IoU observation between the best `<OD>` box and the drawn square was **removed**: this repository ships no box-overlap helper, so computing one in the notebook would have invented a metric (EVAL2). Recorded `SHOULD` deviation: EVAL11 (no baselines — none is meaningful without labelled data).
- Ceilings `MAX_IMAGE_SIDE`, `MAX_NEW_TOKENS`/`DEFAULT_MAX_NEW_TOKENS`, `MAX_TEXT_CHARS`, `NUM_BEAMS` and the full `TASKS` list are surfaced before the model runs, and the notebook performs no validation of its own — every request is checked only by the pipeline's `validate_inputs`/`run` path; the processor's 768 x 768 squash is stated (DAT22/DAT23).
- The default sample is a synthetic drawing generated in code (shapes plus text in Pillow's built-in font); `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- The validator whitelists the rejected `microsoft/Florence-2-large` revision that `docs/WEIGHTS.md` records once in its pin history.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
